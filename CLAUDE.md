# ReGit

Bun workspace: `apps/*` (deployables) and `packages/*` (shared code consumed as TypeScript source, no build step). Shared dependency versions live in the root `catalog`; reference them with `"catalog:"`.

## Conventions

- SvelteKit 3, Svelte 5 runes, experimental async and remote functions are on. Config lives in `vite.config.ts`, not `svelte.config.js`.
- Import app code with `#lib/...`, not `$lib`. Read bindings with `import { env } from 'cloudflare:workers'`, not `platform.env`. In `apps/web`, touch `env` only inside functions: the build imports server modules where bindings don't exist.
- Use the `--space-1` to `--space-7` scale in `theme.css` (2–20px, in rem) for padding, margins and gaps rather than raw values; borders and focus outlines stay in px. Sizes that belong to text (icons, inline avatars, button, bubble and chip padding) use em so they scale with it; `--chat-inset` aligns content with the composer's text.
- Shared components live in `packages/ui`, each with a Svelte CSF story (`*.stories.svelte`). Style with the tokens in `theme.css`.
- The three deployables are `apps/web`, `apps/forge` and the `apps/sandbox` image. Durable Objects, Workflows and containers belong in forge; web binds to them with `script_name: "regit-forge"` and interfaces in `@regit/core`. Canonical writes go exclusively through `RepositoryGit` (`ship`, and `revert` for commits that broke main).
- Forge serves `git.regit.dev` outside Access: clone/fetch requires a hashed, expiring D1 token and current principal membership via `canAccessRepository`. Tokens are read-only and receive-pack is always refused. Contribution forks and a local CLI are deferred.
- Pushes reach forge as Artifacts `cf.artifacts.repo.pushed` events through `triggers.events`, which start the `RepoPushed` Workflow; thread forks share the namespace and are filtered out by their `--` names. Shipping runs as the `ShipThread` Workflow, which calls `RepositoryGit.ship` without running checks and reports back to the coordinator; the test config (`test/wrangler.jsonc`) must declare every Workflow binding too. The test harness doesn't emit these events, so tests call the coordinator's `landed` directly (a ship starts verifying its own commit).
- Main is tested after merge, before deploy: the coordinator runs one `VerifyMain` Workflow at a time on the newest commit (commits landing meanwhile collapse into the next run), which checks it in the repo's `MainSandbox` (its own container, no agent), rechecks failures to rule out flakes, bisects from the last green commit, then runs `.agents/deploy` with the repo's deploy secrets and `REGIT_DEPLOYED_SHA`, the commit it deployed last (ReGit's own deploys forge, then web, needs a `CLOUDFLARE_API_TOKEN` secret, and keeps the deployed sandbox image with `--containers-rollout none` while `apps/sandbox` is unchanged). A culprit's thread gets one hand-back to fix it; otherwise `RevertShip` reverts what it shipped. New threads start from the last green commit. Deploy secrets are sealed with forge's `DEPLOY_SECRETS_KEY` (base64, 32 bytes; an optional secret, so local dev without it can't save deploy secrets) in the coordinator and opened only by `MainSandbox`.
- In wrangler's test harness, `bindingOverrides` only applies to Workers loaded with `configPath`; on an inline `config` it is silently ignored and the real binding is used.
- The agent loop, model clients and sandbox tool clients live in `packages/agent` as plain TypeScript that takes its model, tools and storage as interfaces, so it is unit tested with fakes. `apps/sandbox` is the container's tool server (`bun run image` builds it); it is tested in-process against a temporary git repo. Both run their tests with `bun test` (import from `bun:test`); forge, web and ui use Vitest.
- Leave a one-line `// TODO:` where a deferred follow-up belongs.
- The sandbox image is mise-based: toolchains come from the repository's version files (installed and snapshotted per repo by `AttemptSandbox`; `MainSandbox` snapshots its own container once checks have prepared it) plus `apps/sandbox/mise-system.toml`. It includes Docker, whose daemon `apps/sandbox/docker.sh` starts on first use without iptables, IP forwarding or a bridge network (Cloudflare Containers can't manage them), so builds and networked containers use the host network. The image sets `NO_COLOR`, `FORCE_COLOR=0`, `DO_NOT_TRACK`, non-interactive git and apt, and `REGIT=1`; thread sandboxes add `AI_AGENT=regit`, `REGIT_REPO`, `REGIT_THREAD` and `REGIT_PREVIEW_HOST`, and the main sandbox `CI=true` and `REGIT_REPO`. Locally, containers can't reach the internet over HTTPS (Miniflare's egress sidecar resets it), so tests must not depend on downloads. Forge tests run the sandbox server as a local process through `SANDBOX_URL`; each test file gets its own harness and files run in parallel, so keep files balanced. Tests in a file share the harness without resetting it, so give each test its own repo and thread names. The fake model scripts replies and decisions per repo (from the `repo` in request metadata) and serves them first come, first served, so wait for a repo's threads to finish their turn before scripting its next replies; `bun run --filter @regit/forge test:containers` exercises a real container and toolchain snapshots, so run it after changing container or sandbox code.
- Data shared across repos lives in D1 (`DB`), defined with Drizzle in `packages/db`; forge and web both bind it, and web owns repo creation (D1 plus its own Artifacts binding). After changing `packages/db/src/schema.ts`, run `bun run --filter @regit/db generate`. Per-repo live state stays in Durable Object SQLite. Locally both workers persist to the root `.wrangler/state`, and forge's `dev` applies migrations. Web's remote bindings (Artifacts) proxy through its workers.dev domain, which is behind Access, so non-interactive `dev` needs `CLOUDFLARE_ACCESS_CLIENT_ID` and `CLOUDFLARE_ACCESS_CLIENT_SECRET` set to a service token.
- Long-running services (dev servers, Storybook) are saved in `.agents/services.yml` and run by the sandbox's service manager; agents drive them with the `regit services` CLI through `run`, and logs go to `~/.regit/logs`. Previews are served at `<id>-<service>.regit.run` (one level deep, so the free certificate covers them), routed by forge's `*.regit.run` route to the thread's Durable Object and on to the container port; services must listen on 0.0.0.0.
- Repository checks live in `.agents/checks.yml`: `run` commands and `ask` rules (judged by Jev, advisory unless `blocking`, handoff only) required before `handoff` (the end of an agent turn that changed files; failures go back to the agent) or `deploy` (run on main after it lands, in a separate worktree, `.git/regit-checkout`, prepared by `.agents/setup`). Passes are reused while a check's inputs and the toolchain are unchanged. An `ask` rule that mentions `{intent}` also gets the thread's intent (as Jev state, part of its evidence key) and fails or warns when there is none. Agents record each done-when check as met, unmet or unverified with `record_done_when`; results carry the tree they were observed on and turn outdated when the thread's changes move. The sandbox uses Bun's YAML and glob APIs, so forge tests run its daemon under Bun.
- Agent instructions stay short; guidance for specific tasks lives in skills. Built-in skills (threads, services, toolchains) are in `packages/agent/src/skills.ts`, and repositories add their own as `.agents/skills/<name>/SKILL.md`, which the sandbox discovers and agents load with `load_skill`.
- Quick typed decisions (duplicate and overlap detection between threads) use TypeSafe's Jev (`typesafe/jev`) through `Models.decide`, which calls it via the `regit` AI Gateway; forge tests script its answers with `scriptDecisions` and default to "unrelated".
- `worker-configuration.d.ts` is generated and gitignored. After editing a `wrangler.jsonc`, run `bun run gen`.
- Stories are the component tests: Vitest runs every story in Chromium with accessibility checks, and `play` functions cover interactions. Wrap assertions on anything that animates in with `waitFor`. Story files share one page (`isolate: false`), so don't leave module-level state behind.
- Keep code self-explanatory with minimal comments. Run `bun run check` and `bun run test` before considering work done.
